# 校园失物招领智能匹配：白盒单元测试设计与自动化实践

> 本文是一篇独立的项目测试博客，说明测试工具、学习过程、白盒用例设计、测试数据、自动化方案及测试评价。对应的可执行代码位于 `tests/unit/matching.test.js`。

## 一、为什么选择智能匹配模块做单元测试

项目的智能匹配模块会综合图片、类别、地点、时间和关键词，为一条寻物信息寻找可能对应的招领信息。它直接影响“是否推荐”和“推荐顺序”，同时包含较多判断分支，因此适合使用白盒方法检查内部路径。

本次被测对象是 `js/features/matching.js` 中的六个函数：

| 函数 | 作用 |
| --- | --- |
| `extractKeywords()` | 将“饭卡、学生证、card”等同义词归一为标准关键词 |
| `sameArea()` | 判断两个地点是否属于同一个校园区域 |
| `placeMatch()` | 区分地点相同、同区域和不相关 |
| `timeKey()` | 将自然语言时间归入“今天、昨天、3 天、本周”等时间桶 |
| `calcMatch()` | 按图片 50%、类别 20%、地点 15%、时间 10%、关键词 5% 计算匹配度 |
| `findMatches()` | 过滤无效候选、应用 60 分门槛并按匹配度排序 |

## 二、测试工具与学习过程

### 1. 选用的工具

项目使用 Node.js 内置的 `node:test` 作为测试运行器，使用 `node:assert/strict` 完成断言。选择它有四个原因：

1. Node.js 自带，不需要安装 Jest、Vitest 等第三方包。
2. 支持同步和异步测试，能够直接测试异步的 `calcMatch()`、`findMatches()`。
3. 命令统一，任何组员克隆仓库后都可运行同一批测试。
4. 能生成代码覆盖率结果，适合持续回归。

### 2. 我是如何学习单元测试的

我的学习顺序不是先堆测试数量，而是先理解一个好测试的标准：

1. 阅读 [Node.js Test Runner 官方文档](https://nodejs.org/api/test.html)，学习 `test()`、异步测试、断言和命令行运行方法。
2. 阅读邹欣老师的[《关于单元测试和回归测试》](https://www.cnblogs.com/xinz/archive/2011/11/20/2255830.html)，重点理解测试应当快速、可重复、相互独立，覆盖正常路径和错误路径，并与产品代码一起维护。
3. 采用 Arrange–Act–Assert，即“准备数据—调用函数—断言结果”，先为一个简单分支写用例。
4. 阅读被测源码并画出判断路径，再补齐真/假分支、提前返回、循环命中和边界值。
5. 故意修改一次预期结果，确认测试确实会失败，避免出现“永远通过但没有验证作用”的测试。

## 三、五分钟运行教程

### 1. 准备环境

单元测试需要 Node.js 20 或更高版本。普通打开网页不需要 Node.js。

```bash
node --version
```

### 2. 运行全部测试

在 `campus-lost-found-web` 根目录执行：

```bash
npm test
```

本项目没有第三方测试依赖，因此不需要先执行 `npm install`。也可以直接运行：

```bash
node --test tests/unit/*.test.js
```

### 3. 查看覆盖率

```bash
npm run test:coverage
```

覆盖率用于发现没有执行到的代码路径，但 100% 覆盖率不等于程序一定完全正确，还需要检查断言是否合理，并结合浏览器中的功能测试。

当前实测 `matching.js` 的覆盖率为：行覆盖率 62.96%、分支覆盖率 96.67%、函数覆盖率 81.25%。未覆盖部分主要是依赖表单和弹窗 DOM 的 `submitPublish()`、`closeSuccess()`，它们属于页面交互测试范围；本次白盒单元测试重点覆盖的六个匹配函数均已被执行。

## 四、白盒测试设计

### 1. 采用的方法

本次至少采用了以下白盒用例设计方法：

- **语句覆盖**：让关键词提取、地点判断、时间归类、计分、过滤和排序语句都至少执行一次。
- **判定/分支覆盖**：对 `if` 判断分别构造成立与不成立的数据。
- **条件覆盖**：例如 `p && q && (p.indexOf(q) >= 0 || q.indexOf(p) >= 0)`，分别测试空地点、左侧包含、无包含等条件。
- **路径覆盖**：覆盖同类型提前返回、有图/无图、地点相同/同区域/无关、时间相同/不同等主要组合路径。
- **边界值分析**：重点检查 `score >= 60` 中的 60 分、低于 60 分和最高 99 分。

### 2. 从源码得到的控制流

| 源码判断 | 需要覆盖的路径 |
| --- | --- |
| `name || ''` | 正常文本、`null` |
| 同义词循环 | 命中后 `break`、遍历完仍未命中 |
| `sameArea()` 区域循环 | 某组命中、所有组均未命中 |
| `placeMatch()` | 空地点、完全相同、互相包含、同区域、无关 |
| `timeKey()` 多个 `if` | 今天、昨天、3 天、本周、默认空值 |
| `a.type === b.type` | 同类提前返回、异类继续计算 |
| `visual !== null` | 有图片特征、缺少图片特征 |
| 类别/关键词判断 | 命中、不命中 |
| 地点计分判断 | 相同得 15 分、同区域得 10 分、无关得 0 分 |
| 时间计分判断 | 同时间桶、不同时间桶、缺少时间 |
| `m && m.score >= 60` | 空匹配、刚好 60、低于 60、高于 60 |
| 候选过滤与排序 | 自身、已完成、同类型、有效候选、多个候选降序 |

在梳理这些路径时发现：原代码先判断 `p === q`，导致两个空字符串也会被当作相同地点。现在已增加空值防御分支，并用 `WB05` 固化为回归测试。

## 六、部分测试代码与函数说明

下面的用例验证 `findMatches()` 的关键边界。它既调用 `calcMatch()`，又执行候选过滤，因此能够检查 60 分判定的两个分支。

```js
test('WB12：findMatches 的 60 分边界保留分支和低于边界排除分支', async () => {
  const query = item();
  const exactBoundary = item({
    id: 2,
    type: 'found',
    name: '黑色物品',
    desc: '无明显特征',
    place: '第一田径场'
  });
  const belowBoundary = item({
    id: 3,
    type: 'found',
    place: '第一田径场',
    time: '昨天'
  });
  const data = [query, exactBoundary, belowBoundary];
  const {calcMatch, findMatches} = loadMatching({visual: null, data});

  assert.equal((await calcMatch(query, exactBoundary)).score, 60);
  assert.equal((await calcMatch(query, belowBoundary)).score, 50);
  assert.deepEqual(Array.from(await findMatches(query), match => match.id), [2]);
});
```

- `item()` 是测试数据工厂，先生成一条字段完整的默认信息，再覆盖本用例关心的字段。
- `loadMatching()` 通过源码中仅对 Node.js 生效的导出入口加载真实的 `js/features/matching.js`，测试的不是复制出来的假算法；浏览器运行时不会进入该导出分支。
- `imageSimilarity()` 属于浏览器模型边界，测试时用固定的 `null` 或数值替代，使结果快速且可重复。
- 三个断言分别验证边界分数、低于边界的分数，以及 `findMatches()` 最终是否只保留正确候选。

## 七、测试数据的构造思路

### 1. 默认对象加最小修改

测试数据工厂默认生成一条“黑色折叠伞”寻物信息。每个用例只修改与当前分支有关的字段，可以避免测试地点时被名称差异意外干扰，也使失败原因更容易定位。

### 2. 正向、反向和异常数据成对设计

- 正向：类别相同、地点相同、时间相同、关键词相同。
- 反向：类别不同、跨区域、不同时间桶、无共同关键词。
- 异常：`null`、空字符串、无法识别的具体日期、无候选列表。
- 状态：活动中、已完成、自身记录、同类型记录。

### 3. 边界数据直接由规则反推

匹配门槛是 60，因此不是随便挑两个分数，而是精确构造 60 分和 50 分。完全命中时检查上限 99，避免页面给出“100% 确定”的误导性结果。

### 4. 如何应对测试人员的“刁难”

测试人员可能故意输入重复同义词、混合大小写英文、空地点、无图片、无法识别的日期，或构造同一记录匹配自己、已完成记录再次推荐、多候选乱序等情况。WB01—WB14 已覆盖这些高风险组合。若以后发现新缺陷，应先增加一个能够复现缺陷的失败用例，再修改代码；该用例之后就成为新的回归基准。

## 八、如何实现自动化和每日运行

### 1. 每个人都能在本机运行

统一入口是：

```bash
npm test
```

测试不访问网络、不写数据库、不修改产品数据，彼此没有执行顺序依赖，因此任意组员都能反复运行。

### 2. GitHub Actions 自动回归

仓库中的 `.github/workflows/unit-tests.yml` 会在以下时机运行全部单元测试：

- 每次推送代码；
- 每个 Pull Request；
- 每天北京时间 08:00；
- 团队成员在 GitHub 页面手动触发。

这样一旦某次修改破坏已有行为，提交当天就能发现，而不必等到最终验收。

## 九、对测试设计的评价

### 1. 是否满足测试评估要求

| 评价要求 | 当前情况 | 评价 |
| --- | --- | --- |
| 至少使用白盒方法 | 使用语句、分支、条件、主要路径覆盖，并根据源码判断设计用例 | 满足 |
| 至少 10 个用例 | 共 14 个可自动执行用例 | 满足 |
| 正常、异常、边界情况 | 包含成功匹配、无匹配、空值、缺图、同类、完成状态、60 分边界 | 满足 |
| 自动化且易运行 | 本地统一使用 `npm test` | 满足 |
| 每日构建运行 | GitHub Actions 每日定时，并在 push/PR 时运行 | 满足 |
| 快速、可重复、独立 | 无网络、数据库和随机数依赖；图片模型被稳定替身隔离 | 满足 |
| 测试与产品代码共同维护 | 测试、工作流和源码保存在同一仓库 | 满足 |

### 2. 能否满足整个程序的测试要求

结论是：**这 14 个用例能够满足智能匹配核心模块的单元测试要求，但不能单独证明整个网页不存在问题。**

当前测试充分覆盖了评分、过滤和排序的主要内部路径，也实际发现并修复了“空地点被判相同”的缺陷。不过，MobileNet 模型加载、图片文件解码、OCR、摄像头/文件选择器、DOM 点击流程、不同浏览器兼容性和视觉布局属于模块集成或用户界面范围，不适合只靠这组单元测试判断。

因此完整测试应由三层组成：

1. 本文的自动化单元测试负责匹配算法回归；
2. `tests/MANUAL_TEST_CASES.md` 负责页面主流程和浏览器交互；
3. `tests/fixtures/` 中的图片素材用于识图准确性和模型降级测试。

这种评价没有把“用例数量多”误当成“所有功能都正确”，而是明确了本组测试能证明什么、尚不能证明什么，以及后续应如何补足。
